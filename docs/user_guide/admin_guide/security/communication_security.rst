通信セキュリティ
======================

NVIDIA FLARE は、FL サーバーとクライアント間の通信を保護するための複数のオプションを提供しており、
さまざまな IT インフラストラクチャの要件に柔軟に対応できます。

接続セキュリティのオプション
------------------------------

FLARE は 3 種類の接続セキュリティをサポートしています。

mTLS (相互 TLS)
~~~~~~~~~~~~~~~~~
これはデフォルトかつ最も安全なオプションで、相互 TLS (2-way SSL) を使用します。クライアント/サーバー間の接続には
スタートアップキットに含まれる PKI クレデンシャルが使用され、双方が互いを認証することを保証します。

TLS (片方向 SSL)
~~~~~~~~~~~~~~~~~
このモードでは、サーバー認証のみが必要です。接続の確立にクライアント証明書は不要ですが、サーバーを検証するために
ルート証明書が必要です。サーバーの検証用にカスタムのルート証明書を指定することもできます。

Clear (平文)
~~~~~~~~~~~~~~
メッセージは暗号化されません。これは通常、サーバーが安全なプロキシの背後にデプロイされており、プロキシとサーバー間の
通信がすでに保護されている場合に使用されます。

.. _byoconn:

BYOConn (Bring Your Own Connectivity)
-------------------------------------

FLARE は、以下の要件を満たすカスタムの接続ソリューションをサポートしています。

* クライアントが (直接またはプロキシ経由で) サーバーに到達できること
* 通信経路がメッセージの機密性と完全性を保証すること
* メッセージが明示的に認証されること

メッセージ認証
----------------------

FLARE 2.5 以降では、すべてのメッセージが明示的に認証されます。

1. クライアントは最初にサーバーへログインし、スタートアップキットに含まれるクレデンシャルで認証を行います
2. 検証に成功すると、サーバーはトークンと署名を発行します
3. 以降のすべてのメッセージには、クライアント名、トークン、署名がヘッダーとして含まれます
4. サーバーはすべてのメッセージについてこれらのヘッダーを検証します

この認証は、送信元 (FL クライアント、サードパーティシステム、サーバー自身) にかかわらず、サーバーを経由する
すべてのメッセージに適用されます。

設定
-------------

接続セキュリティは、 `connection_security` および `custom_ca_cert` プロパティを使用して、プロジェクトレベルと
参加者レベルの両方で設定できます。

設定例:

.. code-block:: yaml

   api_version: 3
   name: test25
   description: NVIDIA FLARE sample project yaml file
   connection_security: tls
   custom_ca_cert: /path/of/customRoot.pem

   participants:
    - name: server
      type: server
      org: nvidia
      fed_learn_port: 8002
      admin_port: 8003
      connection_security: clear
    - name: site-1
      type: client
      org: nvidia

この例では次のようになります。

* プロジェクトレベルで指定されているため、プロジェクトのデフォルトは "tls" です
* サーバーは "clear" を使用します (安全なプロキシの背後にあるため)
* クライアントはプロキシへの接続に "tls" を使用します
* `custom_ca_cert` はプロキシサーバーの検証に使用されます

`custom_ca_cert` プロパティは、TLS 接続を行う際のサーバー認証にのみ使用されます。指定されていない場合は、
プロビジョニングシステムによって生成されたルート CA 証明書が使用されます。

`connection_security` が指定されていない場合、デフォルトは mTLS になります。

カスタム CA 証明書を使用する場面
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

利用者によっては、FL クライアントと FL サーバーの間にプロキシを配置して接続を実装する場合があります。FL クライアントは
プロキシサーバーにのみ直接接続し、プロキシサーバーが FL サーバーに接続します。一般的に、FL クライアントはプロキシサーバーへの
接続に片方向 SSL を使用します。この場合、 `custom_ca_cert` はプロキシサーバーが使用する CA 証明書となります。

FL サーバーのマルチアドレス対応
----------------------------------

以前は、FL サーバーはすべての FL クライアントがアクセスするために使用しなければならない単一のアドレスを持っていました。
もう 1 つの制限は、サーバーアドレスをドメイン名として指定する必要があり、IP アドレスがサポートされていなかったことです。
さらに、そのドメイン名はプロビジョニング設定におけるサーバー名としても指定する必要がありました。
この名前はサーバー証明書のコモンネームに設定されるため、63 文字を超えることができませんでした。そのため、63 文字より長い
ドメイン名を使用することは不可能でした。

FLARE 2.6 では、FL サーバーの複数アドレスがサポートされます。この場合、FL サーバーは FL クライアントの接続に使用できる
複数のアドレスを公開できます。利用者の IT ポリシーに応じて、FL クライアントごとに異なるアドレスを使用することもできます。
たとえば、FL サーバーがインターネットからアクセス可能なアドレスと、内部ネットワークからのみアクセス可能なアドレスの
2 つを提供することができます。

サーバーアドレスは、ドメイン名または IP アドレスとして指定できます。

設定例:

.. code-block:: yaml

   participants:
    - name: server
      type: server
      org: nvidia
      fed_learn_port: 8002
      admin_port: 8003
      host_names: [localhost, 127.0.0.1]
      default_host: localhost
      # connection_security: clear
    - name: red
      type: client
      org: nvidia
      connect_to: 127.0.0.1
    - name: blue
      type: client
      org: nvidia
      connect_to: localhost

この例では、FL サーバーが host_names プロパティを使用して、 `localhost` (ドメイン名) と `127.0.0.1` (IP アドレス) の
2 つのホスト名を追加で定義しています。後方互換性のため、default_host プロパティが明示的に定義されていない場合は、
サーバーの名前がデフォルトアドレスとして扱われます。この例では、デフォルトアドレスは `localhost` として明示的に
定義されています。

`host_names` プロパティで指定するアドレスは 255 文字までに制限されます。

ここでは red、blue、silver という 3 つのクライアントが定義されています。 `connect_to` プロパティは、そのクライアントが
使用するアドレスを指定します。当然ながら、指定するアドレスはサーバー側で利用可能でなければなりません。

この例では、クライアント "red" は 127.0.0.1 に接続し、クライアント "blue" は "localhost" に接続し、クライアント "silver" は
サーバーのデフォルトアドレスである "localhost" に接続します。

管理クライアントは 127.0.0.1 に接続します。

この設定が機能するためには、FL サーバーの IT 管理者が、指定されたアドレスが実際にアクセス可能であることを
保証する必要があります。

接続セキュリティと secure_train フラグ
-----------------------------------------

`secure_train` フラグと接続セキュリティは独立していますが、関連があります。

* 接続セキュリティは、接続をどのように行うか (Clear、TLS、または mTLS) を指定します
* 明示的に指定されていない場合、接続セキュリティは `secure_train` に基づいて次のようにデフォルト設定されます

  - `secure_train=True`: mTLS を使用
  - `secure_train=False`: clear を使用

* このデフォルト動作は後方互換性のために維持されています。これら 2 つの設定は以前は 1 つのものとして扱われていたためです
* `secure_train` はプロジェクト全体に適用され、サイトごとに変えることはできません
* 接続セキュリティは、ネットワーク構成の違いに対応するためにサイトごとに変えることができます
* `secure_train` は、プライバシー保護機能 (サイトのローカルフォルダーからのプライバシーリソースの読み込みなど) も有効にします
* `secure_train` フラグは、Simulator を使用する場合を除き、常に True に設定されます

接続セキュリティはサイト固有であり、接続が適切に確立できる限り、サイトごとに異なる設定を使用できます。たとえば次のとおりです。

* サーバーは "clear" の接続セキュリティを使用する
* Site-1 は TLS を使用する
* Site-2 は mTLS を使用する

この柔軟性は、サーバーとサイトの間にプロキシを使用する可能性がある BYOConn (Bring Your Own Connectivity) の
シナリオで特に有用です。そのような場合は次のようになります。

* サイトはサーバーに直接接続しません
* 各サイトは、自身のプロキシへの接続に適した独自の接続セキュリティ設定を持つことができます
* 利用者は、サイトとそれぞれのプロキシとの間で適切な接続セキュリティが設定されていることを保証する必要があります

重要な注意事項
~~~~~~~~~~~~~~~

* すべてのサイトはスタートアップキットを安全に保護する必要があります
* トークンと署名を他者と共有しないでください
* IT インフラストラクチャは、必要なポートの開放を許可する必要があります
* サーバーアドレスは適切に設定され、アクセス可能である必要があります
* カスタム CA 証明書は適切に管理され、保護される必要があります

セキュアなメッセージシリアライゼーション (FOBS)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

分散システムにおいて、メッセージのシリアライゼーションは重要なセキュリティ上の課題です。一般的に使用される Python の
Pickle メカニズムは、デシリアライズ時に任意のコードを実行できるため、安全ではないと考えられています。

NVFLARE は、サーバーとクライアント間のすべてのデータ交換に **FOBS (FLARE Object Serializer)** と呼ばれる
セキュアなシリアライゼーションフレームワークを採用しています。FOBS は **MessagePack** 上に構築された Pickle の
ドロップイン代替であり、明示的にサポートされ登録されたオブジェクト型のみをシリアライズできるようにすることで、
コード実行や改ざん攻撃を防ぎます。

**セキュリティ上の特性:**

- デシリアライズ時の任意コード実行を防止します
- 登録された decomposer によって型のホワイトリスト化を強制します
- コンパクトで言語をまたいで利用できるバイナリエンコーディングのために MessagePack を使用します
- フェデレーテッドノード間でのデータの完全性と型安全性を保証します

詳細な使用方法、decomposer の登録、カスタム型のサポートについては、 :ref:`FOBS リファレンス <serialization>` を
参照してください。
