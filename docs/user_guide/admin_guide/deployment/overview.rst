.. _deployment_overview:

##########################
デプロイメントの概要
##########################

********
はじめに
********

NVIDIA FLARE は、連合学習(Federated Learning)プロジェクトのセットアップに必要な人的調整の手間を減らすため、プロビジョニングと管理者クライアントを活用します。プロビジョニングツールを設定することで、各サイト向けのスタートアップキットを作成できます。
これらのパッケージをすぐに使える状態で各サイトに配布できるため、信頼されたセットアップのもとで連合学習をプロビジョニングし、開始し、運用するプロセスが効率化されます。

プロビジョニング - 配布 - 開始 - 運用
==========================================

プロビジョニング
------------------------------------
FL サーバー、FL クライアント、管理者ユーザー向けのスタートアップパッケージ(スタートアップキット)を生成する方法は複数あります。パッケージの作成・配布・デプロイの方法に応じて、パッケージをプロビジョニングする方法も複数存在します。詳細は :ref:`provisioning` を参照してください。

配布
------------
「配布」とは、プロビジョニングされたソフトウェアパッケージ(スタートアップキット)を各サイトに届ける、または転送することを意味します。

- コマンドライン(CLI)を使ってプロビジョニングする場合、配布は FLARE の責任範囲ではありません。
  任意の配布手段(dropbox、共有ストレージ、メール、FTP など)を使ってパッケージを届けることができます。

- NVIDIA FLARE の Dashboard を使ってプロビジョニングを行う場合は、Dashboard の Web サイトからパッケージを直接ダウンロードできます。


開始
-----
各サイトには、スタートアップパッケージを受け取る、またはダウンロードする組織管理者(org admin)が必要です。組織管理者は自身のパッケージをインストールし、
サービスを開始し、データの場所をマッピングし、認可ポリシーと組織レベルのサイトプライバシーポリシーを設定します。

クライアントのデプロイについては :ref:`provisioned_setup` を、連合認可とプライバシーポリシーの設定方法については :ref:`site_policy_management` を参照してください。

運用
-------
リードサイエンティストや管理者が連合学習のプロセスを制御します。アプリケーションをデプロイするジョブの投入、ステータスの確認、
トレーニングの中止(abort)/シャットダウンなどを行います。

上記の操作をさまざまな方法で実行する方法については、:ref:`operating_nvflare` のセクションを参照してください。

.. _provisioned_setup:

******************************************************************************
プロビジョニングとスタートアップパッケージの配布
******************************************************************************
スタートアップキットパッケージは、FL 参加者が安全に通信できるようにするためのスクリプトと認証情報のセットです。このようなパッケージを
生成するプロセスを、NVIDIA FLARE では **プロビジョニング(Provisioning)** と呼びます。

NVIDIA FLARE には、NVIDIA FLARE の ``provision`` CLI ツールを使う方法と、NVFLARE Dashboard を使う方法の 2 つのプロビジョニング方法があります。

CLI ツールによるプロビジョニング
================================================================
:ref:`provisioning` ページには、プロビジョニングツールの内容と、その基盤となる NVIDIA FLARE Open Provision API の詳細が記載されています。
これを使って、独自の要件に合わせて構成をカスタマイズできます。

プロビジョニングツールのあるディレクトリ内の :ref:`プロジェクト yaml ファイル <project_yml>` を、プロジェクトの要件に合わせて編集します(サーバー、
クライアントサイト、管理者、組織など、すべてがプロジェクトに対して正しいことを確認してください)。

マルチスタディのデプロイメントでは、``api_version: 4`` を設定し、``studies:`` セクションを追加して、スタディごとの
サイト登録と管理者ロールのマッピングを定義します。:ref:`multi_study_guide` を参照してください。

その後、以下のように provision コマンドを実行します(ここでは
project.yml がカレントワーキングディレクトリにあると仮定します):

.. code-block:: bash

    nvflare provision -p project.yml

生成されたスタートアップキットは、デフォルトでは ``provision.py`` を実行した場所に作成されるワークスペースフォルダー内の
プロジェクト名のフォルダーの中の、"prod\_" というプレフィックスが付いたディレクトリに作成されます。

プロビジョニング構成のカスタマイズ
--------------------------------------------------------------------------
上級ユーザー向けに、追加のビルダーを通じてプロビジョニングに追加の動作をカスタマイズできます:

    - **Zip**: スタートアップキットのパスワード保護付き zip アーカイブを作成するには、:ref:`distribution_builder` を参照してください。
    - **Docker Compose** *(非推奨)*: 以前は docker コンテナ経由で NVIDIA FLARE を起動するために使われていました。現行のアプローチについては :ref:`containerized_deployment` を参照してください。
    - **Docker および Kubernetes ランタイムの準備**: 既存のサーバーまたはクライアントのスタートアップキットを :ref:`deploy_prepare_command` で準備します。ランタイム固有のデプロイ手順については、:ref:`containerized_deployment` と :ref:`helm_chart` を参照してください。
    - **CUSTOM**: :ref:`distribution_builder` のように、独自のニーズに応じたカスタムビルダーを構築できます。

パッケージの配布
--------------------------------------
プロビジョニングが完了すると、サーバーおよびクライアントごとのフォルダーにスタートアップパッケージが作成されます。CLI アプローチでは、
すべての参加者と組織/クライアントのホスト情報を収集するだけでなく、参加組織にパッケージを配布する必要もあります。
セキュリティが確保できる限り、メールや sftp などを使って配布できます。

.. attention::

   構成を変更するには、チェックアウトしたバージョンのコードで provision を実行する前に、nvflare/lighter/impl/master_template.yml を
   変更する必要がある場合があります(PYTHONPATH が NVFlare リポジトリをチェックアウトした場所を
   指していることを確認してください)。

   生成されたスタートアップキットの内容は :class:`SignatureBuilder<nvflare.lighter.impl.signature.SignatureBuilder>` によって
   署名されているため、スタートアップキットの内容を直接編集することはできません。ファイルが改変されるとシステムがそれを検知し、
   実行できなくなる可能性があります。

Dashboard UI によるプロビジョニング
================================================================
:ref:`nvflare_dashboard_ui` は、バージョン 2.2.1 で導入された NVIDIA FLARE のオプション機能で、プロジェクト
管理者が Web サイトをデプロイして、各サイトの情報を収集し、スタートアップキットを配布できるようにします。

NVFLARE Dashboard の紹介
--------------------------------------------------
:ref:`nvflare_dashboard_ui` は、dashboard CLI コマンド
``nvflare dashboard --start -i nvflare/nvflare:2.7.2`` でインストール・実行できます(停止は ``nvflare dashboard --stop``)。
イメージ名には、``registry.example.com/nvflare/nvflare:2.7.2`` のように、
ランタイムが pull できる任意のレジストリを指定できます。

Dashboard の起動方法の詳細は :ref:`こちら <dashboard_api>` を参照してください。Dashboard UI の使用方法については :ref:`こちら <nvflare_dashboard_ui>` を参照してください。

Dashboard がセットアップされ、プロジェクトが公開されると、すべての参加者のスタートアップキットを Dashboard からダウンロードできます。

CLI によるプロビジョニングと異なり、情報は Dashboard UI によって収集され、デフォルトのビルダーが使用されるため、カスタマイズのオプションは多くありません。

CLI によるプロビジョニングと比べると、各ユーザーが自分のスタートアップキットをダウンロードするため、スタートアップキットの配布の手間が大幅に簡素化されます。

.. note::

   注記: 各スタートアップキット内の "startup" フォルダーは、コードが動作のためにこの名前に依存しているため、リネームしないことが重要です。
   なお、"transfer" ディレクトリとデプロイされたアプリケーションは、この "startup" フォルダーと同じ階層に作成されます。詳細は
   以下の `NVIDIA FLARE の内部フォルダーおよびファイル構造`_ のセクションを参照してください。

************************************************************************************
開始: NVIDIA FLARE パッケージのデプロイメント
************************************************************************************
このセクションでは、さまざまなケースでのデプロイ方法について説明します。

オンプレミスデプロイメント
==========================================================
プロビジョニングと配布のプロセスを経ると、サイトの組織管理者(Org Admin)はすでにスタートアップキットを受け取っているはずです。
組織管理者は startup ディレクトリに移動し、`start.sh` コマンドを実行してサーバーまたはクライアントを起動します。
注意: サーバーはクライアントより先に起動する必要があります。サーバーとクライアントが接続されると、基本的な連合学習システムが稼働している状態になります。

クラウドデプロイメント
============================================
各クラウド VM インスタンスをオンプレミスのホストと同様に扱い、同じ方法でデプロイすることも当然可能です。
ただし、スタートアップキットをデプロイする前に、VM やセキュリティグループなどのセットアップが必要になります。

NVIDIA FLARE はこれを簡単にしています。特にパブリッククラウド(Azure または AWS)では、クラウドデプロイメント機能により、
たとえば FL サーバーを Azure に、FL クライアントを AWS にデプロイし、さらに別の FL クライアントをオンプレミスに配置するといった、
マルチクラウド/ハイブリッドクラウドのデプロイメントが可能です。

Azure および AWS クラウドへのデプロイ方法は :ref:`cloud_deployment` を参照してください。

Google Cloud への同様のデプロイメントアプローチは、将来のリリースで提供される予定です。

Kubernetes デプロイメント
================================================
プロビジョニング後に ``nvflare deploy prepare`` を使用して、参加者ごとの
Helm チャートと K8s ランチャー構成を生成します。現行の Kubernetes デプロイメント
ワークフローについては :ref:`helm_chart` を参照してください。


.. _starting_fl_servers:

連合学習サーバーの起動
=============================================
FL サーバーは連合学習トレーニングを調整し、すべてのクライアントと管理者
クライアントが接続するメインのハブとなります。

各サーバーのパッケージ内で、"startup" フォルダーにある start.sh ファイルを実行してサーバーを起動します。

rootCA.pem ファイルは、fed_server.json の "ssl_root_cert" から参照されています。別の場所に移動/コピーする場合は、
fed_server.json を変更する必要があります。他の 2 つのファイル、server.crt と server.key についても同様です。

.. note::

   注記: セキュアな gRPC 通信のためには、FL サーバーはプロビジョニング段階で指定されたホスト名に
   バインドする必要があります。そのホスト名が FL サーバーがバインドできるものであることを必ず確認してください。さらに、
   サーバーが通信に使用するポートがファイアウォールによってブロックされていないことも確認してください。

他のマシンのクライアントがサーバーに接続できない場合は、プロビジョニングプロセスでスタートアップキットを生成した際に指定した
ホスト名(project.yml の participants にあるサーバーの名前)が正しい IP に解決されることを確認してください。
FL サーバーが DNS ホスト名のない内部ネットワークにある場合、Ubuntu では、内部 IP とホスト名のエントリを
``/etc/hosts`` に追加する必要があるかもしれません。

.. note::

   注記: ``enable_tensor_disk_offload=True`` を有効にした PyTorch FedAvg ジョブでは、FL サーバーはストリーミングされてきた
   テンソルをサーバープロセスの一時ディレクトリに書き込みます。このディレクトリは、Python の ``tempfile`` により
   ``TMPDIR``、``TEMP``、``TMP``、および OS デフォルト(多くの場合 ``/tmp``)から解決されます。``TMPDIR`` が未設定、存在しない、
   または書き込み不可の場合、Python は暗黙的に別の書き込み可能な一時ディレクトリにフォールバックすることがあります。
   ``startup/start.sh`` を起動するサーバーサービスまたはシェルにおいて、``TMPDIR`` が、想定されるテンソルペイロードに十分な
   空き容量を持つ、既存の書き込み可能なディスクバックのマウントを指すように設定してください。テンソルディスクオフロードでは、
   ``tmpfs`` や ``ramfs`` のような RAM バックの一時ファイルシステムはサーバーのメモリ使用量を削減しないため、避けてください。
   サーバーの IT セットアップの一環として、解決される一時ディレクトリとそのバックとなるファイルシステムの両方を確認してください。

連合学習クライアントの起動
============================================
連合学習トレーニングに参加する各サイトはクライアントです。各クライアントのパッケージは、プロジェクトの
プロビジョニング時に指定したクライアント名にちなんで命名されます。

各クライアントのパッケージ内で、"startup" フォルダーから ``start.sh`` を
実行してクライアントを起動します。

.. tip::

   ``start.sh`` シェルスクリプトを実行する前に、まず NVIDIA FLARE パッケージをインストールする必要があります。NVIDIA FLARE は
   PyPi で公開されており、``python3 -m pip install nvflare`` でインストールできます。

   その後に起動するデプロイ済みアプリケーションによっては、環境に追加の Python パッケージが
   必要になる場合があります。未インストールの場合は、NVIDIA FLARE のインストール後にインストールしてください。NVIDIA FLARE は
   ディープラーニング環境を強制しません。環境のセットアップは完全にユーザーに委ねられています。

.. note::

    注記: デプロイするアプリケーション内でのデータセットの場所によっては、データをどこにマウントするかの調整が必要になる場合があります。

rootCA.pem ファイルは、fed_client.json の "ssl_root_cert" から参照されています。別の場所に移動/コピーする場合は、
fed_client.json を変更する必要があります。他の 2 つのファイル、client.crt と client.key についても同様です。

この連合学習プロジェクトへの参加申請時のクライアント名は、クライアント証明書の CN フィールドに埋め込まれており、
参加者を一意に識別します。そのため、その秘密鍵である client.key は厳重に保護してください。

クライアントが FL サーバーへの接続に成功すると、サーバーとそのクライアントの両方が、クライアントの接続成功を
確認するトークンをログに記録します:

サーバー::

    2020-07-07 03:48:49,712 - ClientManager - INFO - Client: New client abcd@127.0.0.1 joined. Sent token: f279157b-df8c-aa1b-8560-2c43efa257bc.  Total clients: 1

クライアント::

    2020-07-07 03:48:49,713 - FederatedClient - INFO - Successfully registered client:abcd for exampletraining. Got token:f279157b-df8c-aa1b-8560-2c43efa257bc

接続できない場合、クライアントは繰り返し接続を試み、失敗のたびに次のログを記録します::

    Could not connect to server. Setting flag for stopping training. failed to connect to all addresses

サーバーが稼働している場合は、適切な権限が設定されるよう、ファイアウォールのポート設定のトラブルシューティングが
必要になることがあります。これには、リード側の IT 担当者とサイト側の IT 担当者の間での調整が必要になる場合があります。

連合学習管理コンソール
=========================================
各管理コンソールは、サーバーに接続してコマンドを送信できます。各管理コンソールのパッケージは、プロジェクトの
プロビジョニング時に指定したメールアドレスにちなんで命名され、管理コンソールの起動時には認証のために同じメールアドレスを
入力する必要があります。もちろん、管理コンソールクライアントのスタートアップキットをダウンロードしておく必要があります。

管理コンソールとスタートアップキットを使用するには、まず NVFLARE がインストールされている必要があります。

まず、wheel パッケージを以下のようにインストールします::

    python3 -m pip install nvflare[apt_opt]


インストール後、``fl_admin.sh`` ファイルを実行して FL サーバーとの通信を開始できます。
管理コンソールを起動するには、FL サーバーが稼働しており、管理コンソールと FL サーバーの間で
接続が成功している必要があります。プロンプト **User Name:** には、プロジェクトのプロビジョニングで
その管理コンソールに使用したメールアドレスを入力します。

``rootCA.pem`` ファイルは、fl_admin.sh の "ca_cert" から参照されています。別の場所に移動/コピーする場合は、
対応するスクリプトを変更する必要があります。他の 2 つのファイル、client.crt と client.key についても同様です。

この FL プロジェクトに参加するためのメールアドレスは、クライアント証明書の CN フィールドに埋め込まれており、
参加者を一意に識別します。そのため、その秘密鍵である client.key は厳重に保護してください。

.. attention::

   "startup" フォルダーを含むディレクトリへの書き込み権限が必要です。ファイルアップロード用の "transfer" ディレクトリや、
   連合学習の実行のために作成されるディレクトリがここに配置されるためです。詳細は
   `NVIDIA FLARE の内部フォルダーおよびファイル構造`_ を参照してください。


Docker での利用
===================
スキルセットや好みに応じて、pip install で作業することを好むデータサイエンティストもいれば、docker を使うことを好む人もいます。
たとえば、Python、NVFlare、およびオプションのワークロード依存関係がすでにインストールされた
Docker イメージがあるとします。プロビジョニング済みのサーバーまたはクライアントのスタートアップキットを
Docker モードで実行するには、既存のキットを ``nvflare deploy prepare`` で準備します。
準備されたキットには、``startup/start_docker.sh`` と、ジョブごとの Docker コンテナ用の
ランチャー構成が含まれます。

Docker ランタイムの準備については :ref:`deploy_prepare_command` を、
ジョブレベルの Docker イメージ設定については :ref:`launcher_spec` を参照してください。

.. note::

   注記: ``docker run`` で docker 内で FL サーバーを起動する場合は、``--net=host`` を使用してホスト名をその
   docker インスタンスにマッピングしてください。


*******************************************************
運用: 管理者としての連合学習の実行
*******************************************************
連合システムがデプロイされたので、あと少しで運用モードに移行できます。ただし、その前に確認すべきステップが 2 つあります:

- **プリフライトチェック**: システムが正しく機能していることを確認します。
- **ワークロード**: トレーニングコードなどをシステムにどのように提供するかを決定します。

プリフライトチェック
========================================
デプロイ後、すべてのサイトが正しく接続され、正常に機能していることを確認します。

次のコマンドを使用できます:

.. code-block::

    nvflare preflight_check

`preflight_check` の詳細については、:ref:`preflight_check` を参照してください。

ワークロード
========================
ワークロード(通常はトレーニングコードと評価コードを含む)は、複数の方法でデプロイできます:

- **動的にデプロイされるコード**: これは **BYOC** (Bring Your Own Code) 機能です。**custom** フォルダーを使うことで、Python ワークロード(トレーニングコード)をローカルで定義でき、ジョブが投入されると FLARE がサーバーとクライアントの各サイトに自動的にデプロイします。

  この機能は主に、実験や POC の際にデータサイエンティストによって使用されます。セキュリティ上、動的なコードのロードが許されない本番環境の負荷では、実験を実行する前にワークロードを事前インストールしておく必要があります。

- **事前デプロイされるコード**: セキュリティやその他の要件により動的なコードのロードが許されない場合は、実験を開始する前に事前インストールが必要です。ワークロードを含んだ Docker イメージをビルドすることで、アプリケーションとその依存関係を事前インストールできます。

.. note::
    注記: サーバーとクライアントの両方が、ワークロードに必要な依存関係を備えていることを確認してください。たとえば、サーバーとクライアントの両方が `torch.save()` メソッドを使ってモデルのチェックポイントを保存する必要がある場合、PyTorch はサーバーとクライアントの両方にインストールされている必要があります。Docker を使用する場合は、Docker コンテナ内にインストールされている必要があります。


管理コンソールからの連合学習の実行
==========================================================
前のセクション `連合学習管理コンソール`_ で説明したとおり、FL サーバー、FL クライアント、管理コンソール間の
すべての接続が開かれ、すべての参加者が正常に起動していれば、
admin コマンドを使って連合学習プロジェクトを運用できます。:ref:`flare_api` は、スクリプトやノートブックから
これらのコマンドを発行するためにサポートされている Python インターフェースを提供します。

admin コマンドの完全な一覧は :ref:`operating_nvflare` を参照してください。

コマンドを使って FL システムを運用する例については、:ref:`getting_started` セクションの例を参照してください。
