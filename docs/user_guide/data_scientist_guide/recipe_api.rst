.. _recipe_api:

Recipe API リファレンス
==============================================

このページでは、レシピベースのジョブを作成・エクスポート・実行する際に依拠できる、安定版の Recipe API について説明します。また、生成されるジョブの詳細のうち、ユーザー向けの Recipe API ではなく内部実装の詳細に当たるものについても明示します。

レシピジョブの構成要素
--------------------------------------------

ほとんどのレシピスクリプトは 3 つの要素を使用します:

* ``FedAvgRecipe`` や ``CyclicRecipe`` のような具象レシピは、実行したいジョブを記述します。コンストラクタ引数を設定し、必要に応じて Recipe ヘルパーを呼び出し、その後 ``export()`` または ``execute()`` を呼び出します。
* ``SimEnv``、``PocEnv``、``ProdEnv`` のような実行環境は、ジョブをどこで実行するかを記述します。ほとんどのスクリプトはこれを ``recipe.execute(env)`` に渡します。
* ``recipe.execute(env)`` が返す ``Run`` ハンドルを使うと、ジョブ ID の確認、ステータスの確認、結果の取得、ジョブの中止ができます。

自動化やツール開発向けには、``nvflare recipe list --format json`` が機械可読なレシピカタログを返します。カタログのスキーマへのリンクは、このページの末尾にあります。

具象レシピから始める
----------------------------------------

レシピスクリプトは、具象レシピクラスの作成から始めてください。例として、``FedAvgRecipe``、``CyclicRecipe``、``FedOptRecipe``、``FedStatsRecipe``、および ``nvflare recipe list`` で一覧表示される XGBoost 系レシピがあります。

コンストラクタのパラメータは、レシピガイドに記載されているか、以下のコマンドで返される場合に公開 API です:

.. code-block:: shell

   nvflare recipe show <recipe-name> --format json

基底型の ``Recipe`` は、具象レシピが共有する動作を定義します。ほとんどのスクリプトは基底型を直接インスタンス化しません。公開されているコンストラクタの仕様は、各具象レシピのドキュメント化されたコンストラクタです。

レシピの実行
------------------------

すべての具象レシピは、共通の実行インターフェースをサポートします:

``recipe.export(job_dir, server_exec_params=None, client_exec_params=None, env=None)``
   現在のレシピ定義を、デプロイ可能な NVFlare ジョブディレクトリとしてエクスポートします。``env`` が指定された場合、レシピはエクスポート前に環境固有の処理を適用できます。実行パラメータの辞書はジョブ定義の一部となるため、シークレット値を含めてはいけません。:ref:`recipe_secrets` を参照してください。

``recipe.execute(env, server_exec_params=None, client_exec_params=None)``
   現在のレシピ定義を実行環境を通じて実行し、``Run`` ハンドルを返します。実行パラメータの辞書にシークレット値を含めてはいけません。Python プロセスが Recipe のエクスポートフラグを受け取った場合、``execute`` はジョブを送信する代わりにエクスポートを行います:

   .. code-block:: shell

      python job.py --export --export-dir /tmp/nvflare/job

``recipe.run(env, server_exec_params=None, client_exec_params=None)``
   環境を通じて直接ジョブを送信し、``Run`` ハンドルを返します。ほとんどのユーザー向けの例では、エクスポートフラグが機能し続けるように ``execute`` を使用すべきです。実行パラメータの辞書にシークレット値を含めてはいけません。

Recipe ヘルパーはレシピオブジェクトを変更します。これから作成するジョブに対しては、``export()`` または ``execute()`` の前にヘルパーを呼び出してください。ジョブがエクスポートまたは送信された後にヘルパーを呼び出しても、既に作成されたそのジョブは変更されません。同じレシピオブジェクトからの将来のエクスポートや実行にのみ影響します。

レシピのカスタマイズ用ヘルパー
------------------------------------------------------------

レシピは、生成されるジョブに対する一般的なカスタマイズのための公開ヘルパーを既に提供しています。生成された設定ファイルを手で編集する代わりに、これらのヘルパーを使用してください。

設定ヘルパー:

``recipe.add_client_config(config, clients=None)``
   生成されるクライアントアプリのトップレベル設定パラメータを追加します。``clients`` を省略した場合、設定は生成されるすべてのクライアントアプリに適用されます。この辞書は平文で保存されるため、シークレット値を含めてはいけません。

``recipe.add_server_config(config)``
   生成されるサーバーアプリのトップレベル設定パラメータを追加します。この辞書は平文で保存されるため、シークレット値を含めてはいけません。

これらの設定ヘルパーは、タイムアウトやストリーミングのチャンクサイズといった、ドキュメント化されたトップレベルの設定項目のためのものです。コンポーネント配置用の API ではないため、生成される ``components``、``workflows``、``executors`` のリストを置き換える目的で使用しないでください。

ファイルパッケージングヘルパー:

``recipe.add_client_file(file_path, clients=None)``
   ファイルまたはディレクトリを、生成されるクライアントアプリのパッケージに同梱します。

``recipe.add_server_file(file_path)``
   ファイルまたはディレクトリを、生成されるサーバーアプリのパッケージに同梱します。

``clients`` を受け付けるヘルパーは、生成される特定のクライアントアプリを対象とします。これにはサイトごとのクライアントアプリが必要です。これをサポートするレシピでは、レシピ構築直後に ``set_per_site_config`` を呼び出してください。レシピは、最初のクライアント対象ヘルパーを適用する前にそれらのアプリを準備し、``clients`` 内の各名前は設定済みのサイトごとのクライアントアプリと一致していなければなりません。デフォルトの全クライアント向けトポロジーでは、対象を指定した呼び出しは、生成されるジョブから変更を暗黙に取り落とすのではなくエラーを送出します。また、未知のサイト名は、そのサイトに空のアプリをデプロイするのではなくエラーを送出します。

フィルターヘルパー:

``recipe.add_client_input_filter(filter, tasks=None, clients=None)``
   サーバーから受信するタスクデータに対するクライアント側の入力フィルターを追加します。

``recipe.add_client_output_filter(filter, tasks=None, clients=None)``
   サーバーへ送信するタスク結果に対するクライアント側の出力フィルターを追加します。

``recipe.add_server_input_filter(filter, tasks=None)``
   クライアントから受信するタスク結果に対するサーバー側の入力フィルターを追加します。

``recipe.add_server_output_filter(filter, tasks=None)``
   クライアントへ送信するタスクデータに対するサーバー側の出力フィルターを追加します。

共通ヘルパー:

``recipe.add_decomposers(decomposers)``
   生成されるサーバーおよびクライアントアプリのパッケージに decomposer を登録します。

``recipe.enable_log_streaming(*file_names)``
   デフォルトの Recipe ログストリーミングコンポーネントを追加します。ファイル名が指定されない場合、レシピは ``log.json`` をストリーミングします。

``recipe.enable_tensor_streaming(format="pytorch", tasks=None, tensor_send_timeout=30.0, wait_send_task_data_all_clients_timeout=300.0)``
   サーバーと、生成されるすべてのクライアントアプリに、対になるテンソルストリーミングコンポーネントを追加します。フォーマットはレシピの ``server_expected_format`` と一致している必要があります。

ユーティリティヘルパー:

``add_experiment_tracking(recipe, tracking_type, tracking_config=None, client_side=False, server_side=True, clients=None)``
   TensorBoard、MLflow、Weights & Biases など、サポートされている実験トラッキングのレシーバーを追加します。``client_side=True`` の場合、``clients`` でクライアント側レシーバーを受け取るサイトを限定できます。サイトごとに異なるトラッキング先を設定するには、異なる ``tracking_config`` の値でサイトごとに 1 回ずつ呼び出してください。MLflow の場合、``tracking_config`` を省略するとローカルストレージが使用され、実験名はデフォルトで ``<recipe-name>-experiment`` になります。実行名のサフィックスは、サーバー側トラッキングでは ``<recipe-name>-Server``、クライアント側トラッキングでは ``<recipe-name>-Client`` がデフォルトです。トラッキング用の認証情報は実行サイトの環境またはマウントされたシークレットファイルに保持し、``tracking_config`` には決して入れないでください。

``add_cross_site_evaluation(recipe, submit_model_timeout=600, validation_timeout=6000, participating_clients=None)``
   レシピ/フレームワークがサポートしている場合に、トレーニングレシピにサイト横断評価を追加します。

``add_final_global_evaluation(recipe, participating_clients=None, validation_timeout=6000)``
   クライアントにローカルモデルの提出を求めることなく、PyTorch レシピの永続化されたグローバルモデルの最終評価を追加します。

サイトごとの設定とメタデータのヘルパー
----------------------------------------------------------------------------

NVFlare 2.9 では、公開されている Recipe 設定インターフェースには以下も含まれます:

``set_per_site_config(recipe, config)``
   空でない、サイト名をキーとするレシピ固有の設定を指定します。レシピ構築直後、クライアントのカスタマイズの前に 1 回だけ呼び出してください。各具象レシピは、自身のワークフローに合わせてサイトごとの辞書を解釈します。組み込みの FedAvg、FedEval、XGBoost の各レシピは、少なくとも ``min_clients`` 個のエントリを必要とします。このヘルパーはマッピングを検証して保存します。レシピは、最初のクライアントカスタマイズの直前、またはエクスポートや実行の前に、クライアントアプリを一度だけ作成します。ネストされた値はジョブ定義の一部となるため、シークレット値を含めてはいけません。

``recipe.configured_sites()``
   適用されたサイトごとの設定から、トップレベルのサイト名を返します。このメソッドは、サイトが接続されていることを示すものでも、実行環境を置き換えるものでもありません。

``set_recipe_meta(recipe, key, value)``
   生成されるジョブの選択されたメタデータを ``JobMetaKey`` で設定します。受け付けられるキーは、:data:`nvflare.apis.job_def.USER_SETTABLE_JOB_META_KEYS` のメンバーと完全に一致します。このヘルパーで設定できないもの: NVFlare 内部が管理する実行時/送信時メタデータ、専用のコンストラクタフィールドを持つキー(``min_clients``、``mandatory_clients``)、およびサーバーが送信時に管理者セッションから割り当てる ``study``。キーごとの値の形と例については、Recipe ガイドのレシピメタデータのセクションを参照してください。メタデータは平文で保存されるため、シークレット値を含めてはいけません。

同じキーに対してメタデータの呼び出しを繰り返すと、そのキーの以前のヘルパーの値が置き換えられます。異なるメタデータキーは蓄積されます。専用のコンストラクタフィールドと重複するキーは、優先されるのではなく拒否されます。受け付けられたキーについては、ヘルパーの値が生成される ``meta.json`` に現れる値になります(メタデータは最後にマージされます)。``RESOURCE_SPEC`` が生成されるジョブのサイトごとのリソース仕様を上書きする場合、ヘルパー呼び出し時点で既に登録されている仕様に対しては警告が発行されますが、その後に追加された仕様は警告なしに上書きされます。

レシピパラメータからシークレットを排除する
------------------------------------------------------------------------------------

レシピパラメータはジョブ定義の一部であり、シークレットの伝送手段ではありません。レシピのコンストラクタや変更系ヘルパーを通じて指定された値は、生成される設定ファイルに平文でシリアライズされる可能性があります。これには、``train_args``、``task_args``、``eval_args``、``per_site_config``、タスクデータとメタデータ、サーバー/クライアントの設定オーバーライド辞書、実行パラメータ、レシピメタデータ、トラッキング設定、および ``add_client_config`` / ``add_server_config`` に渡される辞書が含まれます。これらの値に、実際のパスワード、API キー、アクセストークン、秘密鍵、その他の認証情報を **決して** 含めてはいけません。

この契約は、トップレベルのパラメータ値だけでなく、ネストされた文字列にも適用されます。シークレットの環境変数名、参照プレースホルダー、マウントされたシークレットファイルへのパスは設定情報であり、指定してかまいません。シークレットの値そのものは実行サイト側に留めなければなりません。

ミスを検出するために、レシピはエクスポートや実行の前に、ヒューリスティクス(よく知られたトークン形式、パスワードらしいフラグ名やキー名、高エントロピー文字列)を用いて現在のパラメータをスキャンし、値が実際のシークレットのように見える場合に ``nvflare.recipe.secrets.PotentialSecretWarning`` を発行します。``recipe.export()`` はさらに、エクスポートされたジョブの生成済み設定ファイルもスキャンします。このスキャンはベストエフォートです。あらゆる認証情報を発見できるわけでも、指定された値を安全にするわけでもありません。警告が出ないことは、パラメータが安全であることの証明にはなりません。各警告を調査し、実際のシークレットはサイト側に留め、参照はサポートされているランタイム境界でのみ使用してください。標準の ``warnings.filterwarnings`` の仕組みは、検出結果が誤検知であると確認した後にのみ使用してください。NVFlare は検出器の警告を合成されたソース位置から発行するため、Python の警告フォーマッタが、フラグの立った値を含むユーザーのソース行をエコーすることはありません。サポートされていないことが判明しているパラメータ内の有効な参照は、暗黙に受け入れられるのではなく ``UnsupportedSecretRefWarning`` を発行します。

シークレットを実行時に利用可能にする方法は、サポートされているものとして 2 つあります:

* **サイトの環境から読み取る(推奨)。** 各サイトで環境変数を設定するか、シークレットファイル(例えば Kubernetes の Secret ボリューム)をマウントし、トレーニングスクリプト内で ``os.environ`` を使うか、マウントされたファイルを開いて読み取ります。シークレットがジョブ定義に入ることは一切ありません。マウントされたシークレットファイルへの *パス* をレシピパラメータで渡すのは問題ありません -- パスはシークレットではないからです。

* **サポートされているランタイム境界でシークレット参照を使う。** 実際のシークレットの代わりに、サポートされているレシピの値にプレースホルダーを入れます。環境変数には ``secret_ref`` を、シークレットを含むファイルには ``secret_file_ref`` を使用します:

  .. code-block:: python

     from nvflare.recipe.secrets import secret_file_ref, secret_ref

     recipe = FedAvgRecipe(
         ...,
         train_args=f"--epochs 5 --api-key {secret_ref('MY_API_KEY')}",
     )
     recipe.add_client_config(
         {"service_password": secret_file_ref("/var/run/secrets/service/password")}
     )

     # In site-side component code:
     from nvflare.utils.configs import get_client_config_value

     service_password = get_client_config_value(fl_ctx, "service_password")

  エクスポートされたジョブには ``${secret:MY_API_KEY}`` と ``${secret:file:/var/run/secrets/service/password}`` のみが含まれます。参照は、以下の明示的なランタイム境界においてのみ解決されます:

  * NVFlare のタスクスクリプトランナーまたはサブプロセスランチャーが消費するコマンド引数。これらのランナーを使用する場合の、レシピの ``train_args``、``task_args``、``eval_args``、``script_args`` が含まれます。NVFlare はまず通常の設定変数を展開し、コマンドをトークン化した後、スクリプトまたはプロセスが開始する直前に各参照を解決します。トークン化の後に解決することで、スペースを含むシークレットが 1 つの引数として維持されます。サブプロセスランチャーは、直接呼び出される、または先頭が ``env`` でラップされた ``sh``/``bash`` および PowerShell のコマンド文字列内の参照を拒否します。これは限定的な安全策であり、汎用的なコードインタープリタ検出器ではありません。別のシェル、別のラッパーの背後に隠れたシェル、``python -c`` など、別のプログラムがコードとして解釈する引数には決して参照を入れないでください。代わりに、子プロセスの環境変数を通じてシークレットを渡すか、呼び出されるコマンドの内部でマウントされたファイルから読み取ってください。

  * ``get_job_config_value``、``get_client_config_value``、``get_server_config_value`` によって実行時のジョブ JSON ファイルから明示的に読み取られる値。典型的には、レシピが ``add_client_config`` または ``add_server_config`` でトップレベルの値を追加し、サイト側のコードが対応する専用のゲッターを通じてそれを読み取ります。ネストされた文字列値内の参照は、値が読み取られるときに再帰的に解決されます。辞書のキーは解決されません。これらの生ファイル用ヘルパーは ``{SITE_NAME}`` のような通常のプレースホルダーを展開しないため、この方法で消費される値にそれらのプレースホルダーを組み合わせないでください。内部のクライアントランチャー用タイムアウト/カウントのオーバーライドはサブプロセスのランタイム設定にコピーされるため、シークレット参照を解決せずに拒否します。参照は、サイトのコンポーネントコードがこれらのゲッターを通じて直接読み取る値に対して使用してください。

  任意のコンポーネントコンストラクタ引数、ジョブメタデータ、パッケージ化されたカスタムファイル、その他のジョブアーティファクトでは、参照はプレースホルダーのまま保持され、シークレットの受け渡し手段にはなりません。それらのケースでは、ユーザーコード内でサイトの環境変数またはマウントされたファイルを読み取ってください。特に、Flower の ``extra_env`` と ``run_config`` の値はシークレット参照をサポートしません。

  環境変数またはファイルが利用できない場合、設定ゲッターまたはスクリプト/プロセスの起動は、欠落している参照を特定するエラーで失敗しますが、シークレット値がエラーに含まれることは決してありません。解決された値はランタイムのメモリ内にのみ存在し、生成されたジョブ設定に書き戻されることはありません。

環境変数は、その参照を使用するサーバーまたはクライアントのジョブプロセスの環境に設定する必要があります。ネイティブプロセスの POC および本番デプロイメントでは、そのプロセスが継承する環境で設定できます。Docker や Kubernetes のジョブコンテナは、任意のホストシェル変数やホストのマウントを自動的に継承しません。ランチャー/コンテナの仕様を設定して、変数を注入するか、ファイルを実際のジョブコンテナ内にマウントしてください。参照されるファイルは、消費するプロセスまたはコンテナの内部で、空白や波括弧を含まない同一のパスに存在しなければならず、そのアイデンティティのみが読み取り可能であるべきです。

Kubernetes の場合は、Secret のキーを環境変数またはマウントされたファイルとしてジョブコンテナに投影し、対応する参照ヘルパーを使用してください。Recipe API が Kubernetes の Secret を Secret 名とキーで直接照会することはありません。

なお、外部プロセス実行では、コマンドライン引数(解決されたシークレット参照を含む)は、他のコマンドラインツールと同様に、実行サイトのローカルなプロセス一覧から見えます。トレーニングスクリプト内で環境変数またはマウントされたファイルからシークレットを読み取れば、これも回避できます。コードと設定されたコンポーネントは、解決された値を出力しないようにもしなければなりません。参照の解決はエクスポートされたジョブから値を排除しますが、ユーザーコードが生成する出力をサニタイズすることはできません。

スレッド方式のシミュレーションは、インプロセスのクライアントスクリプトを並行実行し、プロセスグローバルな ``sys.argv`` と環境を共有します。シミュレーターでシークレットを含むコマンド引数を使う場合は外部プロセス実行を使用するか、可能であればインプロセスのクライアントごとの引数分離に頼るのではなく、コード内でサイトローカルのシークレットを直接読み取ってください。

実行環境
----------------

ほとんどのスクリプトは環境を ``recipe.execute(env)`` に渡します。組み込みの環境には ``SimEnv``、``PocEnv``、``ProdEnv`` があります。

ほとんどのレシピスクリプトは環境のメソッドを直接呼び出しません。以下は、実行環境を実装する人のために列挙しています。

``deploy(job) -> str``
   レシピが生成したジョブをデプロイし、ジョブ ID を返します。

``get_job_status(job_id) -> Optional[str]``
   サポートされている場合、現在のジョブステータスを返します。

``abort_job(job_id) -> None``
   実行中のジョブの停止を要求します。

``get_job_result(job_id, timeout=0.0) -> Optional[str]``
   ジョブが完了した場合は結果のワークスペースパスを返し、結果が準備できていないかサポートされていない場合は ``None`` を返します。

``stop(clean_up=False) -> None``
   環境のリソースを停止し、オプションで一時的なワークスペースをクリーンアップします。

これらのメソッドは主に環境の実装者向けです。ユーザーコードでは、環境を直接呼び出すのではなく ``recipe.execute(env)`` を優先すべきです。

Run ハンドル
------------------------

``recipe.execute`` と ``recipe.run`` は、ジョブが送信されると ``Run`` オブジェクトを返します。``Run`` は以下を公開します:

``run.get_job_id()``
   環境のジョブ ID を返します。

``run.get_status()``
   利用可能な場合、最新のステータスを返します。

``run.get_result(timeout=0.0, clean_up=True)``
   結果を待機し、最終的なステータス/結果をキャッシュし、環境を停止して、利用可能な場合は結果のワークスペースパスを返します。

``run.abort()``
   実行中のジョブの中止を環境に要求します。

依拠できるもの
----------------------------

依拠できるのは、ドキュメント化された具象レシピのコンストラクタパラメータ、ドキュメント化された Recipe のメソッド、ドキュメント化されたヘルパー関数、``ExecEnv`` のメソッド、``Run`` のメソッド、および ``nvflare recipe`` コマンドのドキュメント化された JSON フィールドです。

以下は内部の詳細であり、レシピスクリプトで使用すべきではありません:

* プライベート属性(名前が ``_`` で始まる属性を含む)
* 生成されるジョブの内部構造と、ネストされた生成済みジョブオブジェクト
* レシピの内部にある生成済みジョブ属性
* 生成されたメタデータ辞書の直接変更
* 生成された deploy-map の内部構造
* Recipe ヘルパーが使用する内部フィールド

ワークフローが、名前付きの Recipe ヘルパーでカバーされない任意のコンポーネント配置を必要とする場合は、低レベルの Job API ワークフローを使用するか、繰り返し現れるパターンのために新しい名前付き Recipe ヘルパーを追加してください。

レシピカタログ JSON
--------------------------------------

``nvflare recipe list --format json`` は、利用可能なレシピの機械可読なリストを返します。成功時のレスポンス構造は安定しており、:download:`recipe_catalog.schema.json <../../schemas/recipe_catalog.schema.json>` に記述されています。レシピを検出するツールは、そこにドキュメント化されたフィールドに依拠できます。

``nvflare recipe list --schema`` は、このコマンドのコマンドライン引数を記述します。これはカタログ出力のスキーマとは別物です。
