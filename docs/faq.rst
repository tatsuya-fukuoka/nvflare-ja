.. _FAQ:

############################
よくある質問
############################

************
一般
************

#. NVIDIA FLARE とは何ですか?

    NVIDIA FLARE は、協調コンピューティングのために設計された汎用フレームワークです。この協調コンピューティングフレームワークでは、ワークフローは集約ベースの連合学習(Federated Learning)(通常 Fed-Average ワークフローと呼ばれます)に限定されず、アプリケーションもディープラーニングに限定されません。NVIDIA FLARE は本質的に、マルチスレッド環境で動作するメッセージングシステムです。

#. NVIDIA FLARE は何の略ですか?

    NVIDIA Federated Learning Application Runtime Environment の略です。

#. NVIDIA FLARE は Tensorflow や PyTorch に依存していますか?

    いいえ。NVIDIA FLARE は、汎用的な協調コンピューティングフレームワークを実装した Python ライブラリです。協調コンピューティングワークフローを実行するために定義する :ref:`Controllers <controllers>`、:ref:`Executors <executor>`、:ref:`Tasks <tasks>` は完全に独立しています。

#. NVIDIA FLARE はディープラーニングモデルのトレーニング専用に設計されていますか?

    いいえ。NVIDIA FLARE は、あらゆる協調コンピューティングワークフローをサポートできる通信フレームワークを実装しています。これはディープラーニング、機械学習、あるいは単純な統計ワークフローでも構いません。

#. NVIDIA FLARE に GPU は必要ですか?

    いいえ。ハードウェア要件は、:ref:`Controller <controllers>` ワークフローとクライアントの :ref:`Tasks <tasks>` に実装されている内容にのみ依存します。クライアントのトレーニングタスクは通常 GPU アクセラレーションの恩恵を受けます。サーバーの :ref:`Controller <controllers>` ワークフローは、GPU を必要とする場合もしない場合もあります。

#. NVIDIA FLARE はどのように協調コンピューティングフレームワークを実装していますか?

    NVIDIA FLARE の協調コンピューティングは、:ref:`Controller/Worker <controllers>` のやり取りによって実現されています。

#. Controller とは何ですか?

    :ref:`Controller <controllers>` は、タスクを実行する Worker を制御・調整する Python オブジェクトです。Controller はサーバー上で実行されます。Controller は協調コンピューティングワークフロー全体を定義します。その制御ロジックの中で、Controller は Worker にタスクを割り当て、Worker からのタスク結果を処理します。

#. Worker とは何ですか?

    Worker はタスク(スキル)を実行できるものです。Worker はクライアント上で動作します。

#. Task とは何ですか?

    :ref:`Task <tasks>` は、:ref:`Controller <controllers>` からクライアントの Worker に割り当てられる作業(Python コード)の単位です。タスクの割り当て方法(broadcast、send、relay)に応じて、タスクは1つ以上のクライアントで実行されます。タスクで実行されるロジックは :ref:`Executor <executor>` で定義されます。

#. Learnable とは何ですか?

    Learnable は、サーバーが管理する連合学習アプリケーションの成果物です。DL ワークフローでは、Learnable は学習対象となる DL モデルの側面です。例えば、一般的にはモデルの構造ではなくモデル重みが Learnable の対象となります。スタディの目的に応じて、Learnable は関心のある任意のコンポーネントになり得ます。Learnable は、クライアントの Shareable オブジェクトから集約される抽象オブジェクトであり、DL 固有のものではありません。任意のモデルやオブジェクトにすることができます。Learnable は Controller ワークフローの中で管理されます。

#. Shareable とは何ですか?

    :ref:`Shareable <shareable>` は、単純に2つのピア(サーバーとクライアント)間の通信です。タスクベースのやり取りにおいて、サーバーからクライアントへの Shareable は、クライアントが実行するタスクのデータを運びます。クライアントからサーバーへの Shareable は、タスク実行の結果を運びます。これを DL モデルのトレーニングに適用すると、タスクデータには通常、クライアントがトレーニングするためのモデル重みが含まれ、タスク結果にはクライアントからの更新されたモデル重みが含まれます。Shareable の概念は非常に汎用的で、タスクにとって意味のあるものであれば何でも構いません。

#. FLContext とは何ですか? どのような情報が含まれますか?

    :ref:`FLContext <fl_context>` は NVIDIA FLARE の主要な機能の1つで、すべての :ref:`FLComponent <fl_component>` タイプ(Controller、Aggregator、Executor、Filter、Widget など)のあらゆるメソッドから利用できます。FLContext オブジェクトには、FL 環境のコンテキスト情報、すなわちシステム全体の設定(ピア名、ジョブ ID / 実行番号、ワークスペースの場所など)が含まれます。FLContext には Engine と呼ばれる重要なオブジェクトも含まれており、これを通じてシステムが提供する重要なサービス(イベントの発火、利用可能な全クライアント名の取得、補助メッセージの送信など)にアクセスできます。

#. イベントとは何ですか? どのように処理されますか?

    :ref:`イベント <event_system>` により、:ref:`FLComponent <fl_component>` のサブクラスであるすべてのオブジェクトに動的な通知を送ることができます。すべての FLComponent はイベントハンドラーです。

    イベントメカニズムは pub-sub(出版-購読)のような仕組みで、データ共有のためのコンポーネント間の間接的な通信を可能にします。通常、データの生成側がイベントを発火してデータを公開し、他のコンポーネントは購読しているイベントを処理してそのイベントのデータを消費します。fed イベントメカニズムでは、この pub-sub をネットワーク境界を越えて行うことさえ可能です。

#. Controller ワークフローをサポートするために NVIDIA FLARE で実装できる追加コンポーネントには何がありますか? また、それらはどこ(サーバーまたはクライアント)で実行されますか:

    LearnablePersistor - サーバー
        LearnablePersistor は、Learnable オブジェクトの状態を保存するためにサーバー向けに実装されるメソッドです。例えば、永続化のためにグローバルモデルをディスクに書き込みます。
    ShareableGenerator - サーバー
        ShareableGenerator は2つのメソッドを実装するオブジェクトです。learnable_to_shareable は Learnable オブジェクトをクライアントに共有するデータ形式に変換し、shareable_to_learnable はクライアントからの shareable データ(または集約された shareable データ)を使用して learnable オブジェクトを更新します。
    Aggregator - サーバー
        Aggregator は、クライアントの Shareable オブジェクトでサーバーに返されたデータをサーバー上で集約するために使用するアルゴリズムを定義します。
    Executor - クライアント
        Executor は、Shareable オブジェクトに含まれるデータに対してクライアントが実行するアルゴリズムを定義します。例えば DL トレーニングでは、Executor がトレーニングループを実装します。クライアント上には、異なるタスク(トレーニング、検証/評価、データ準備など)を実行するように設計された複数の Executor を配置できます。
    Filter - クライアントとサーバー
        :ref:`Filters <filters>` は、サーバーとクライアント間で相互に転送される Shareable オブジェクト内のデータの変換を定義するために使用されます。フィルターは、クライアントまたはサーバーのいずれかがデータを送信または受信する際に適用できます。"task_data_filters" と "task_result_filters" がクライアントとサーバーでいつ適用されるかの詳細は、:ref:`Filters <filters>` ページの図を参照してください。
    FLComponent のサブクラスである任意のコンポーネント
        上で説明したすべてのコンポーネントタイプは :ref:`FLComponent <fl_component>` のサブクラスです。さまざまな目的のために独自の FLComponent サブクラスを作成できます。例えば、特定のイベントをリッスンしてそのイベントのデータを処理(分析、ディスクや DB への書き出しなど)するコンポーネントを作成できます。

運用
**************

#. :ref:`プロビジョニング <provisioning>` とは何ですか?

    NVIDIA FLARE には Open Provision API が含まれており、相互に信頼されたシステム全体の設定(スタートアップキット)を生成できます。これにより、すべての参加者が異なる場所から NVIDIA FLARE システムに参加できるようになります。この相互信頼は Open Provision API の必須機能であり、各参加者は設定内の情報によって他の参加者を認証します。設定には通常、以下が含まれます(ただしこれらに限定されません):

        - ドメイン名、ポート番号、IP アドレスなどのネットワーク探索情報
        - 参加者およびルート認証局の証明書などの認証用クレデンシャル
        - ロール、権利、ルールなどの認可ポリシー
        - 署名などの改ざん防止メカニズム
        - 個々の参加者を簡単に起動できるデフォルトのコマンドラインオプション付きシェルスクリプトなどの便利なコマンド

#. Provision ツールはどのような種類のスタートアップキットを生成しますか?

    Open Provision API はスタートアップキットの生成に柔軟性を持たせていますが、通常、プロビジョニングツールは FL サーバー、FL クライアント、Admin クライアント向けの安全なスタートアップキットを生成するために使用されます。

#. 各種類のスタートアップキットにはどのようなファイルが含まれますか? これらのファイルは何のために、誰が使用しますか?

    スタートアップキットには、FL サーバー、FL クライアント、Admin クライアント間の安全な接続を確立するために必要な設定と証明書が含まれます。これらのファイルは、サーバーとクライアント間のアイデンティティと認可ポリシーを確立するために使用されます。スタートアップキットは、ロールに応じて FL サーバー、クライアント、Admin クライアントに配布されます。開発目的では、システム間や単一ホスト上のプロセス間の接続を簡素化するために、セキュリティを限定したスタートアップキットを生成することもできます。詳細は Open Provision API の "poc" 機能を参照してください。

#. スタートアップキットを適切な人に配布するにはどうすればよいですか?

    スタートアップキットの配布は本質的に柔軟で、メールや共有ストレージを介して行うことができます。API では、配布を自動化するビルダーコンポーネントを追加できます。

#. プロビジョニングの後は何が行われますか?

    プロビジョニング後、Admin API を使用してジョブを FL サーバーに送信すると、サーバー上の JobRunner がそれを取得してデプロイ・実行できます。

#. NVIDIA FLARE におけるアプリケーションとは何ですか?

    :ref:`アプリケーション <application>` は、クライアントとサーバーの設定、および Controller/Worker ワークフローの実装に必要なカスタムコードを定義する、名前付きのディレクトリ構造です。

#. NVIDIA FLARE アプリケーションの基本的なディレクトリ構造はどのようなものですか?

    通常、アプリケーションの設定は ``config/`` サブディレクトリで定義され、Controller と Worker のエグゼキューターへのパスを定義します。カスタムコードは ``custom/`` サブディレクトリで定義でき、認可ポリシーで定義されたルールに従います。

#. アプリケーションはどのようにデプロイしますか?

    アプリケーションは admin コマンドの ``submit_job`` を使用してデプロイします。さらに細かい設定として、どのサイトにどのアプリをデプロイするかを指定する deploy_map の定義とともに、アプリをジョブとしてパッケージ化できます。デプロイメントは FL サーバー上の JobRunner によって自動的に行われます。

#. すべての FL クライアントは同じアプリケーション設定を使用する必要がありますか?

    いいえ、同じアプリケーション設定を使用する必要はありません(実際にはそうすることが多いですが)。FL クライアントの機能は、Task と Executor の実装、およびイベントに対するクライアントの応答によってカスタマイズできます。

#. Admin クライアントと FL クライアントの違いは何ですか?

    :ref:`FLARE Console <operating_nvflare>` は、サーバーのコントローラーワークフローの状態を制御するために使用され、サーバーとのみやり取りします。FL クライアントはサーバーをポーリングし、サーバーの状態に基づいてタスクを実行します。Admin クライアントが FL クライアントと直接やり取りすることはありません。

#. Admin クライアントはどこで実行しますか?

    :ref:`FLARE Console <operating_nvflare>` は、通常、研究者のワークステーションまたはラップトップ上でスタンドアロンプロセスとして実行されます。

#. Admin クライアントでは何ができますか?

    :ref:`FLARE Console <operating_nvflare>` は、サーバーとクライアントの起動・停止、アプリケーションのデプロイ、FL 実験の管理など、FL スタディのオーケストレーションに使用されます。

#. トレーニング終了時にグローバルモデルを取得するにはどうすればよいですか? 定義したモデルとキーが一致しない問題を解決するにはどうすればよいですか?

    :ref:`FLARE Console <operating_nvflare>` で download_job コマンドを使用すると、ジョブの結果を admin の transfer フォルダに取得できます。モデルは使用した persistor に応じて dict 形式で保存されるため、PTFileModelPersistor を使用した場合は、PTModelPersistenceFormatManager がモデルをキー "model" の下に保存するので、``model.load_state_dict(torch.load(path_to_model)["model"])`` のようにアクセスする必要があるかもしれません。

#. カスタムファイルが見つからないというエラーが出るのはなぜですか?

    カスタムコードの実行(BYOC - Bring Your Own Code とも呼ばれます)は、現在、各サイトの認可ポリシーによって管理されています。認可ポリシーは、サイトのワークスペースの ``local`` フォルダにある ``authorization.json`` ファイルで定義されます。
    これは :ref:`サイトポリシー管理 <site_policy_management>` システムの一部です。

    **デフォルトの BYOC 権限:**
    プロビジョニング時に、NVFLARE は以下のデフォルト BYOC 権限を持つ ``authorization.json.default`` ファイルを作成します:

    - **project_admin** および **lead** ロール: BYOC を使用可能(``"byoc": "any"``)
    - **org_admin** および **member** ロール: デフォルトでは BYOC を使用不可(``"byoc": "none"`` または BYOC 権限なし)

    特定のユーザーロールに対してカスタムコードの実行を有効化または制限するには、認可ポリシーで ``byoc`` 権限を設定する必要があります。例えば、``authorization.json`` では以下のようにします:

    .. code-block:: json

        {
          "format_version": "1.0",
          "permissions": {
            "lead": {
              "byoc": "any"
            },
            "org_admin": {
              "byoc": "none"
            }
          }
        }

    この例では、"lead" ロールのユーザーはカスタムコードを含むジョブを送信できますが、"org_admin" ユーザーはできません。
    ``byoc`` 権限には ``"any"``、``"none"`` を設定できるほか、特定の組織やユーザーにスコープすること(例: ``"o:org_name"`` や ``"n:username"``)もできます。認可ポリシーの詳細は :ref:`連合認可 <federated_authorization>` を参照してください。

セキュリティ

#. NVIDIA FLARE におけるセキュリティの範囲はどこまでですか?

    セキュリティは多面的なものであり、NVIDIA FLARE API だけで完全に制御・提供できるものではありません。Open Provision API は、共有された自己署名証明書と認可ポリシーによる GRPC を用いた、基本的な通信とアイデンティティのセキュリティの例を提供します。これらのセキュリティ対策で十分な場合もありますが、提供されている API を使って拡張することもできます。

#. データプライバシーについてはどうですか?

    NVIDIA FLARE には、FL 中のデータプライバシーを支援するいくつかの技術が備わっています: 差分プライバシーと準同型暗号です(:ref:`プライバシーフィルター <filters_for_privacy>` を参照)。

****************************************
クライアント関連の質問
****************************************

#. FL トレーニング中に FL クライアントが参加するとどうなりますか?

    FL クライアントはいつでも FL トレーニングに参加できます。FL クライアントをどう管理するかはワークフローのロジック次第です。

#. FL サーバーが FL クライアントに到達するために、連合学習クライアントは何らかのポートを開放する必要がありますか?

    いいえ、連合学習トレーニングでは、FL クライアントがインバウンドトラフィックのためにネットワークを開放する必要はありません。サーバーがクライアントに一方的なリクエストを送ることはなく、クライアントのリクエストに応答するのみです。

#. クライアントは複数の GPU でトレーニングできますか?

    トレーニング用エグゼキューターを :ref:`MultiProcessExecutor <multi_process_executor>` の中に配置することで、マルチ GPU トレーニングを行えます。

#. FL クライアントはどのように識別されますか?

    連合学習クライアントは、実行時にサーバーが発行する動的に生成された FL トークンによって識別されます。FL クライアントが最初に FL トレーニングに参加する際、まず FL サーバーにログインリクエストを送信する必要があります。ログインプロセス中に、FL サーバーとクライアントは双方向認証のために TLS 証明書を交換する必要があります。認証が成功すると、FL サーバーはクライアントに FL トークンを送信します。FL クライアントは、以降のグローバルモデルのリクエストおよびすべてのモデル更新操作において、この FL トークンを使用して自身を識別します。

#. 同じマシンから複数の FL クライアントを実行できますか?

    はい。FL クライアントはマシンの IP ではなく FL トークンによって識別されます。各 FL クライアントは、それぞれ独自の FL トークンとインスタンス名を持ちます。インスタンス名は、そのクライアントに特定のコマンドを発行する際に使用しなければならないクライアント名です。

#. 同じクライアントパッケージを使用して、同じクライアントの複数のインスタンスを実行できますか?

    はい、同じクライアントパッケージから FL クライアントの複数のインスタンスを起動できます。各 FL クライアントは一意のインスタンス名(例: "flclient1"、"flclient1_1"、"flclient1_2" など)によって識別されます。admin ツールからそのクライアントに特定のコマンドを発行するには、インスタンス名を使用する必要があります。

#. 連合学習クライアントがクラッシュするとどうなりますか?

    連合学習クライアントは、1分に1回 FL サーバーにハートビートを送信します。FL クライアントがクラッシュし、FL サーバーがそのクライアントからのハートビートを 10 分間(サーバーの設定または ``local/resources.json`` ファイルの "heart_beat_timeout" で設定可能)受信しなかった場合、FL サーバーはそのクライアントをトレーニングクライアントのリストから削除します。

#. FL クライアントは連合学習トレーニングの途中で参加または離脱できますか?

    はい、FL クライアントは FL トレーニングの途中でいつでも参加または離脱できます。クライアントは、サーバーの現在のラウンドのグローバルモデルを取得して FL トレーニングに参加します。離脱時には、クライアントが離脱し、サーバーに設定された "heart_beat_timeout" の期間ハートビートが受信されなかった後、FL サーバーが自動的にその FL クライアントを削除します。admin ツールを使用している場合は、"abort" および "shutdown" コマンドを使用してクライアントを正常に停止することを推奨します。

#. Scatter and Gather ワークフローで、参加している FL クライアント数が必要な最小クライアント数を下回った場合はどうなりますか?

    FL クライアントは認証を通過すると、現在のラウンドのグローバルモデルをリクエストして、すぐに FL トレーニングを開始できます。他のクライアントを待つ必要はありません。クライアントは自身のトレーニングを終えると、集約のために更新をサーバーに送信します。ただし、サーバーが他のクライアントから十分な更新を受信していない場合、FL サーバーは次のラウンドの FL トレーニングを開始しません。トレーニングを終えた FL クライアントは、次のラウンドのモデルを待機します。

#. Scatter and Gather ワークフローで、最小クライアント数を超える数の FL クライアントが更新モデルを送信した場合はどうなりますか?

    FL サーバーは、必要な最小数の FL クライアントからの更新を受け付け、サーバーに設定された "wait_after_min_clients" の時間待機した後、モデルの集約を開始します。その後に受信された更新は破棄されます。すべてのクライアントは次のラウンドのグローバルモデルを取得して、次のラウンドの FL トレーニングを開始します。

#. クライアントはどのように連合学習トレーニングからの離脱を判断しますか?

    FL クライアントは常にサーバーに次に実行すべきタスクを問い合わせます。:ref:`コントローラー <controllers>` がどのようにクライアントにタスクを割り当てるかを参照してください。

****************************************
サーバー関連の質問
****************************************

#. FL サーバーがクラッシュするとどうなりますか?

    FL サーバーがクラッシュすると、実行中のジョブは中断されます。続行するには、FL サーバーを再起動してジョブを再送信する必要があります。

#. なぜ FL サーバーが特定のラウンド以降にクラッシュし続けるのですか?

    消費メモリ量が利用可能なリソースを超えるような形で増加していないか確認してください。プロセスが過剰にメモリを消費すると、オペレーティングシステムがプロセスを強制終了することがあります。

#. 連合学習サーバーに GPU は必要ですか?

    いいえ、FL サーバーをデプロイするためにサーバー側に GPU を用意する必要はありません。ただし、特定のハンドラーが GPU を必要とする場合があります。サーバー上で GPU を無効にするには、サーバーを実行するシェルスクリプトに以下を含めます::

        export CUDA_VISIBLE_DEVICES=

#. FL サーバーのネットワークでは、ファイアウォールでどのポートを開放する必要がありますか?

    gRPC がデプロイされるポートを制御する :ref:`project.yaml <project_yml>` の設定に応じて、外部のクライアントが FL サーバーに到達できるよう、FL サーバーのネットワークでそのポートを開放する必要があります。

#. 連合学習サーバーがロードバランサーの背後にある場合はどうなりますか?

    現在、連合学習は複数の FL サーバー間のロードバランシングをサポートしていません。

**********************************************************
トレーニングフロー全体に関する質問
**********************************************************

#. 連合学習サーバーはどのように FL の停止タイミングを判断しますか?

    Scatter and Gather ワークフローの場合、FL サーバーは "start_round" から "num_rounds" まで実行します。FL サーバーは、現在のラウンドが "num_rounds" に達するとトレーニングを停止します。他のワークフローの場合は、ワークフロー内のロジックがその判断を行うことができます。

#. FL クライアントを自分の機関内で実行しながら、FL サーバーを AWS 上で実行できますか?

    はい、project.yml ファイルのサーバーの cn として AWS インスタンス名を使用してください。(例: ec2-3-99-123-456.compute-1.amazonaws.com)

#. クライアントごとに異なるアプリケーションをデプロイするにはどうすればよいですか?

    デスクトップ上で個々のクライアント用のアプリケーションフォルダを編集し、admin ツールで個々のクライアントにアップロードしてデプロイできます。各クライアントは独自のアプリケーション設定で実行できます。

#. あるクライアントのトレーニングが誤動作している、または想定外の挙動をしていることに管理者が気づいた場合、どうすればよいですか?

    管理者は、指定したジョブの FL クライアントトレーニングを中止するコマンド ``abort job_id client client_name`` を発行できます。client_name を指定せずにコマンドを発行すると、コマンドはすべてのクライアントに送信されます。モデルトレーニングの性質上、FL クライアントが完全に停止するまで少し時間がかかる場合があります。クライアントのステータスが "stopped" になっているかどうかは、"check_status client client_name" コマンドで確認してください。

#. クライアントへの admin コマンドの応答が返ってくるまでに長い遅延があるのはなぜですか?

    クライアントへの admin コマンドはサーバーを経由します。何らかの理由でコマンドがネットワークによって遅延した場合や、クライアント側のコマンド処理に時間がかかる場合、admin コンソールでは応答に遅延が生じます。デフォルトのタイムアウトは 10 秒です。"set_timeout" コマンドを使用してコマンドのタイムアウトを調整できます。このタイムアウト値を小さくしすぎると、admin コマンドがクライアントに届かず実行されない場合があります。

#. コマンドが失敗することがあるのはなぜですか?

    クライアントのステータスを確認しようとしたときに、サーバーがすでにモデルの転送で忙しく、コマンドのための余分な帯域がない場合、コマンドがタイムアウトすることがあります。その場合は、しばらく待ってから再試行してください。

********************
既知の問題
********************

#. サーバーの IP が変わった場合、admin サーバーが元のホストとポートにバインドされたままになるため、admin クライアントが接続できなくなることがあります。回避策としては、FL サーバーを手動で再起動することが考えられます。再起動時にホストが更新後の IP に解決されてバインドされます。
#. メモリ不足はいつでも発生する可能性があり、特にサーバーとクライアントを同じマシンで実行している場合に起こりやすくなります。これによりサーバーが予期せず停止することがあります。
#. マルチ GPU で実行中のクライアントに対して ``shutdown client`` を呼び出した後、プロセス(sub_worker_process)が残ることがあります。回避策は、``shutdown`` コマンドの前に ``abort client`` を実行することです。
#. スナップショットが破損した状態にあると、サーバーがジョブを復元しようとしてスタックすることがあります。これを解決するには、project.yml で snapshot_persistor ストレージ用に設定された場所(デフォルトでは ``/tmp/nvflare/jobs-storage``)からスナップショットを削除します。その後、``abort_job`` でサーバー上のジョブを停止できるはずです。
